

# AppWorld Agent Playbook

## 1. Workflow and API discipline
1. Read the task literally. List every constraint: who, which items, what filter, exact note/description text, file path, format.
2. Never guess API names or parameters. Run `apis.api_docs.show_api_descriptions(app_name=...)`, then `apis.api_docs.show_api_doc(app_name=..., api_name=...)` before first use of each API. Copy exact parameter names and check the response schema. There is no `list_notes`, `show_contacts` or `supervisor.show_account`; check the docs. Examples of exact names: file_system uses `directory_path` and `compressed_file_path`; review APIs use `title`/`text`; `update_song_review` takes `review_id` and no `song_id`.
3. Only pass `access_token` if the doc lists it. Some APIs take NO `access_token` (e.g. spotify `show_song`, `show_album`, `show_artist`, `search_songs`, `search_artists`, `show_song_reviews`), and passing one is rejected. Write endpoints and library/liked/recommendation endpoints require it. A 401 means the token is missing or you have not logged in to that app. `show_song_queue` has no pagination. Some APIs take a single id rather than a list.
4. Authentication: get passwords via `apis.supervisor.show_account_passwords()`, which returns a list of `{account_name, password}`; pick the entry with `next(...)`. Get your own identity from `apis.supervisor.show_profile()`; do not invent emails. The username is the account email (`show_profile()['email']`) for most apps. The phone app uses the phone number (`show_profile()['phone_number']`). If login fails with 'Invalid credentials', try the other identifier and check `show_api_doc(app, 'login')`. Log in to EACH app you use and keep each app's own `access_token` in its own variable. Re-do login in the same code cell if earlier variables might be undefined (NameError).
5. Do not wrap calls in `try/except: pass`. Swallowed errors cause silent partial work. Let errors surface and read the message, which lists the allowed parameters. On a 409 'already exists', find the existing object's id and update it. Do not retry the same failing call.
6. Pagination: list endpoints default to `page_limit=5` (max 20). For EVERY list call (liked songs/albums, downloaded songs, library, playlists, transactions, requests, notes, contacts, friends), loop `page_index` from 0 with `page_limit=20` until an EMPTY page is returned. Collect the full list first, then mutate. Do not delete while paginating.

- Prefer server-side filters when the doc offers them, then still paginate to an empty page: spotify `search_artists(genre=, min_follower_count=, page_limit=20)` (no access_token), venmo `status='pending'`, phone `search_contacts(relationship=)` / `phone_number=`, `show_directory(substring=, entry_type='files', recursive=False)`. 'At least N' maps to inclusive `min_*`. Print the result count and a sample before acting.

- **Exceptions to the pagination loop**: `file_system.show_directory` takes NO `page_index`/`page_limit` (allowed: `access_token, directory_path, substring, entry_type, recursive`); passing them raises 'Unexpected parameter'. It returns the complete list of absolute path strings in one call, so call it once. Never wrap a paginated loop in `try/except` with a fallback call, because when the loop never sees an empty page it hits the 1000-request limit. Use the returned paths directly as `source_file_path`, and take the filename with `path.rsplit('/', 1)[-1]` (no `os`). `show_song_queue` also has no pagination.
7. The sandbox forbids `os` and similar modules. Use the file_system app APIs for files.
8. Dates: do NOT use `datetime.now()` or `date.today()`; the sandbox clock is fake. Use `apis.phone.get_current_date_and_time()` (no args, no access_token; returns e.g. `{'date': 'Sunday, June 04, 2023', 'time': '11:55 PM'}`; there are no `datetime` or `current_datetime` keys) and parse with `datetime.strptime(d['date'], '%A, %B %d, %Y')`. Parse API timestamps with `datetime.fromisoformat`. 'This year' means the year of that date. 'Last N days including today' means today-(N-1) .. today. 'Last month' and 'yesterday' are relative to that date. Date filters may or may not be inclusive, so also filter on each record's own timestamp in Python and print boundary items.
9. Keep scripts incremental. Run read-only discovery first, then do the mutating calls in a final step. If a run fails midway, check which side effects already happened so they are not duplicated.

- Make writes idempotent and verify afterwards: check state first (e.g. `show_artist_following` before `follow_artist`; `show_sent_payment_requests` before creating requests), create target directories before `move_file` (`overwrite=False`, `retain_dates=True`), then re-read the state to confirm the change before `complete_task()`. Do not re-run a creation cell after a partial failure.

## 2. Final answer rules (`apis.supervisor.complete_task`)
- If the task asks a QUESTION (what / which / how many / how long / title of...), call `complete_task(answer=<value>)`. The value must be a bare number or string with only what was asked: no sentence, no units, no extra text. Apply any rounding the task requests. Always try to find the answer. Do not call `complete_task(status='fail')` just because the first path failed; try other APIs first.
- If the task is an ACTION (add, remove, like, follow, unfollow, send, request, reject, comment, create, export, delete), call `complete_task()` with NO answer. Never pass counts, amounts, ids, lists, or messages. A non-empty answer makes the answer check fail even when the state change is correct.
- `complete_task` accepts only `answer` and `status`. Call it exactly once, only after all state changes succeeded and you have printed and sanity-checked the results (non-empty, plausible counts).

## 3. Inspect real data; never guess fields
- Before writing filter logic, print one raw item of every list response (keys and values) and check the doc's `response_schemas`. Many past errors were KeyErrors from assumed schemas. Examples: Spotify `show_song` has `duration` in seconds, not `duration_ms`. Playlist/album detail may use a `songs` list of dicts with `id` rather than `song_ids`. A received payment request may have no `status` key. Contacts use `relationships` (a list) and `phone_number`. Venmo transactions carry `sender`/`receiver` objects with emails. `search_notes` returns only metadata, so call `show_note` for content. Prefer API filter params (e.g. `status='pending'`) when available.
- Do not use `.get(key, default)` with defaults like `[]`, `0` or `''` on keys you have not verified, and do not use `if 'key' in resp` to skip data silently. These hide wrong field names and lead to destructive mistakes, such as removing every album because the song list came back empty. Index directly, or assert the result is non-empty.
- For text/file content (bills, notes, messages), print 1-2 full samples before writing a parser. Locate the labelled total ('Total', 'Total Amount', 'Amount due'). Do not take the first number matched by a regex.
- Before any bulk or mutating action, print the candidate set (ids + key fields) and its size, plus keep-set and remove-set sizes for destructive operations. Check them against the task wording.

## 4. Resolve task semantics and select the right entities
- Use the data source the task names. 'recommended' means `show_recommendations`, 'liked' means `show_liked_songs`, 'song library' means `show_song_library`, 'album library' means `show_album_library` (then `show_album` for its songs), and playlists mean `show_playlist_library` + `show_playlist`. 'Downloaded', 'liked', 'library' and 'following' are different lists. Do not substitute a broader search. After fetching, apply the extra filters (genre, year, date range) yourself, using detail APIs like `show_song`/`show_album` for missing fields.
- People: 'roommates', 'coworkers', 'friends', 'family' and named persons come from `apis.phone.search_contacts` (use the `relationship` filter, paginate all pages) and are matched by email/phone to the other app's users. Do not approximate with the Venmo friend list, all contacts, or the first search hit. Print the matches before acting.
- Apply every qualifier. 'Reject requests from friends and roommates' means filter pending requests by sender against those specific sets, not all pending requests.
- If the task refers to a message/note/file containing instructions (e.g. 'Laura asked for...'), READ it first (`search_text_messages`, `show_text_message_window`, notes) and apply its exact criteria (genre, director, format) to the content you send. When a search returns several plausible items (several notes), open each and compare title, content and `created_at` against the task. Do not take the first match. Deduplicate lists unless told otherwise.
- 'Last' / 'most recent': sort explicitly by timestamp. Ordering words are literal: 'played so far including the current one' means queue positions <= the current song's position. An album counts as downloaded only if ALL its songs are downloaded.
- 'Least/most/newest' questions: aggregate over ALL pages and all requested sources (e.g. song + album + playlist libraries) before taking min/max.
- Artist questions (e.g. 'most played song by X'): `search_songs` is fuzzy and returns other artists. Filter by `artists[*].name == X` or artist id, paginate fully, then take the max by the requested metric (play_count, like_count, rating) from `show_song`/`show_artist_songs`.
- Venmo: to ASK for money use `create_payment_request(user_email, amount, description, access_token)`. `create_transaction` SENDS money, so do not use it for requests. Use the exact description text from the task. Bill split = total / (roommates + 1). For 'send the money back' or 'haven't paid yet' tasks, check direction (sender/receiver), approved status, date window and sender email on the exact transactions referenced. Use `approve_payment_request` / `deny_payment_request` to resolve requests.
- Spotify exports/cleanups: deduplicate by title plus artist set and join artists with the requested separator. Do destructive steps (remove, delete_account) only after the export has been written and verified. For a 'new' playlist, create a fresh one rather than reusing an existing one, unless told otherwise.

## 5. Task-specific procedures (learned from failures)

### Queue 'played so far' tasks
- Call `show_song_queue`, print `position`/`is_current` for every item, find `cur = the item with is_current True`, and act ONLY on items with `position <= cur.position`. Print the selected ids and their count versus the full queue size before mutating. Never act on the whole queue for 'played so far'. 'Remaining'/'upcoming' means `position > cur.position`.

### Play most/least listened song tasks
- Identify the collection the task names: the album via `search_albums` with an exact title match, or the user's own playlist via `show_playlist_library`. Get its songs from the `songs` list (album/playlist detail) or `song_ids`, and assert the list is non-empty.
- Call `show_song` for EVERY song and print (id, title, play_count). Check for ties and pick the max/min explicitly. Check `show_api_doc('spotify','show_song_privates')` for any per-user play or listen field before relying on the global `play_count`.
- Play with `play_music(song_id=..., access_token=...)`, then verify with the current-song or `show_song_queue` API that the current song id equals the chosen id and belongs to the collection. Then call `complete_task()` with no answer.

### Venmo 'some people already paid, request the rest' tasks
- Find the dinner date from the task ('yesterday' means current phone date minus 1) and the note's `created_at`. When several similar notes exist, choose the one matching the described event and date; print all candidates.
- Decide 'already paid' only from received transactions (`direction='received'`) whose `created_at` is on or after the event date (use `min_created_at`). Match by sender email, and also check that the amount matches the share and the description is plausibly related. Do NOT treat an old unrelated transaction from the same person as payment. Print each person -> email -> paid? decision.
- Resolve note names to emails using `search_contacts` with the stated `relationship` (e.g. 'coworker'). If a first name matches several contacts, disambiguate by relationship and print the ambiguity instead of taking the first hit. Request each share amount with the exact description given.

### File export tasks
- Use paths exactly as written in the task (e.g. `~/backups/x.csv`). Do NOT expand `~` into a guessed /home/<name> path. Log in to `file_system` first (username is the email) and pass its own access_token. The file API has no `write_file`; check `show_api_descriptions('file_system')` and use `create_file`, or `update_file` if the file already exists (check `file_exists`). Create the directory with `directory_path=`.
- Write plain `Title,Artists` rows without wrapping fields in quotes unless a value contains a comma. Join artists with the requested separator. Gather songs with direct indexing (`album['songs']`, `playlist['song_ids']`; use `show_album`/`show_playlist` for details) rather than `.get(key, [])`, and print the per-source and deduplicated counts. Re-read the file with `show_file` before any destructive step such as `delete_account`.

## 6. Quick recipes that worked

- **Pagination helper (use for EVERY list call, no exceptions)**:
```python
def fetch_all(fn, **kw):
    out, i = [], 0
    while True:
        page = fn(page_index=i, page_limit=20, **kw)
        if not page: break
        out += page; i += 1
    return out
```
This includes `show_following_artists`, `show_alarms`, `show_liked_songs`, `show_downloaded_songs`, `show_*_library`, `search_*`. A bare `show_following_artists(access_token=)` or `show_alarms(access_token=)` returns only 5 items. `file_system.show_directory` is the exception: it has NO page params and returns a list of absolute path strings.
- **Alarm 'move/shift' tasks**: find the target by a case-insensitive substring of `label` (e.g. 'sleep') in the fully paginated list. NEVER create or delete alarms for a move task. Compute the new time from the existing `time` and call `update_alarm(alarm_id, access_token, time='HH:MM')` changing only that field. If the target is not found, print all alarms and re-check pagination instead of creating one. A 409 'already exists' means an alarm with that time and label exists, so find it.
- **Spotify album/playlist fields**: a `show_album_library` item has `song_ids`; `show_album(album_id)` (no token) has `songs[*].id`; `show_playlist(playlist_id, access_token)` has `songs[*].id`. Index them directly, never `.get('song_ids', [])`. For 'album is downloaded', require `song_ids` non-empty and all in the downloaded-id set; print per-album counts. For 'liked or downloaded' cleanups, print keep and remove sizes for songs AND albums before removing.
- **Follow/unfollow by song relation**: collect artist ids from `songs[*].artists[*].id` (liked songs / playlist songs). For 'indie songs in playlists', get genre via `show_song`. The unfollow set is `fetch_all(show_following_artists)` minus the artist ids found. Finish with `complete_task()` and no answer.
- **File-system listings and bills**: `show_directory` returns absolute strings such as '/home/<user>/photos/Bali/', even when you pass '~/...'. Use returned paths as-is (name via `p.rstrip('/').split('/')[-1]`); do not string-replace '~/'. Bills are usually in per-type subfolders (e.g. `~/bills/internet/`); list with `recursive=True`, `entry_type='all'`. Files may exist as both `.pdf` and `.txt` for the same month: count each month ONCE using only `.txt`, filter by the year in the filename, and read the `Total Amount => $N` line (regex on 'Total Amount', not the first number). Print month -> amount before summing. To archive each dir use `compress_directory(directory_path=, compressed_file_path='~/photos/vacations/<name>.tar', delete_directory=True, access_token=)`; list the subdirs first (excluding the target 'vacations' dir) and print them.
- **File organizing by date**: list files with `show_directory(entry_type='files', recursive=False)`, call `show_file` for `created_at`, parse with `datetime.fromisoformat`, compare month/year to the task, then `move_file` to `<dir>/<Name>/<original filename>`.
- **Aggregate over song/album/playlist libraries**: paginate each library fully, collect song ids into a set (album/playlist detail uses `songs[*].id`), call `show_song` (no token) for `release_date`/`play_count`, then take min/max and answer with the bare title.
- **'Most recommended/liked artist'**: paginate the whole list, count artist names across all songs, take the max, and print the top few counts to check ties.
- **Year boundaries are literal**: 'after 2021' means year > 2021 and 'before 2021' means year < 2021 (2021 excluded). Use `datetime.fromisoformat(release_date).year`. For 'library AND playlists' tasks, process both sources (library `song_id`, playlist `songs[*].id`) and print the removal count per source first.
- **Venmo totals** ('how much sent/received to my roommates since DATE'): get group emails via `search_contacts(relationship=...)`, then `venmo.show_transactions(direction='sent'|'received', min_created_at='YYYY-MM-DD', page_limit=20)` over all pages (check `show_api_doc` for `direction`). Filter on `receiver['email']` (sent) or `sender['email']` (received), sum `amount`, and answer with the bare number.
- **Spotify durations**: `show_playlist(playlist_id, access_token)` returns `songs` with `duration` in seconds. Pass `access_token` for your own private playlists, otherwise you get a 422. Sum per playlist and convert to minutes (/60). For workout tasks, read today's `duration_mins` from the note (weekday from `get_current_date_and_time`) and choose a playlist with total >= that value. Start it with `spotify.play_music(playlist_id=..., access_token=...)`.
- **Editing note content**: `search_notes`, check the title, then `show_note`. Change only the targeted line with an exact string replace (`'[ ] Item'` -> `'[x] Item'`), print the new content, then `update_note(note_id, access_token, content=<full new content>)`.
- **Alarms**: paginate `show_alarms`, identify the target by `label` (case-insensitive), and use `update_alarm(alarm_id, access_token, time='HH:MM' | enabled=bool)` as a partial update with only the changed fields. Apply the 'rest' to every other alarm, then re-list and print the final states.
- **Bulk phone message deletion**: `search_text_messages(phone_number=...)` -> `text_message_id` -> `delete_text_message`, and `search_voice_messages(phone_number=...)` -> `voice_message_id` -> `delete_voice_message`. Collect all ids first, then delete both kinds when the task names both.

HARD RULES (these override convenience; most recent failures came from breaking them):

1. PAGINATE EVERYTHING, INCLUDING `search_contacts`, `search_songs`, `search_notes`, and every `show_*_library`. A call without a `page_index` loop returns only 5 items. Write a helper `fetch_all(fn, **kw)` that loops `page_index` from 0 with `page_limit=20` until an EMPTY page, and use it for every list call. Never stop because a page was shorter than the limit. After collecting, print the count. If a contact group such as friends+roommates yields very few entries (<10), re-check that you paginated.

2. ARTIST QUESTIONS: Never use `search_songs(query='<artist name>')` alone, since it is fuzzy and truncated. Get the artist's id from `search_artists(query=name)` by exact name match, then call `search_songs(artist_id=<id>, page_index=..., page_limit=20)` over all pages. Take the max of `play_count` and answer with the bare title. Also verify that every candidate song lists that artist.

3. PLAYLIST CONTENTS: Items from `show_playlist_library` do NOT contain songs. For each playlist_id, call `show_playlist(playlist_id=..., access_token=...)` and read `pl['songs']` (a list of dicts with `id`, `title`, `artists`). Never use `.get('songs', [])` or `.get('song_ids', [])` on library items, because that silently gives an empty result. Print the per-playlist song counts. For removal tasks ('remove songs released after/before YEAR from library and playlists'), do this:
   a) Fetch the full library via `show_song_library`, and every playlist via `show_playlist`.
   b) Call `show_song(song_id)` for every distinct song id from both sources, and compute release year with `datetime.fromisoformat(release_date).year`.
   c) Build the removal set per source: library ids and (playlist_id, song_id) pairs. Print both.
   d) Remove using `remove_song_from_playlist` for each pair and `remove_song_from_library` for each library id.
   e) Re-fetch both sources and assert that no song matching the criterion remains. 'After 2021' means year > 2021. If the playlist removal set is empty, double-check that you really called `show_playlist`, since a result of 0 is usually a bug.
   A song may be in a playlist but not in the library, and vice versa; evaluate each source independently.

4. SPOTIFY EXPORTS (unique songs from song library + album library + all playlists): Build the set from three sources. (i) `show_song_library` items (`song_id`, `title`, `artists[*].name`). (ii) For each album in `show_album_library`, call `show_album(album_id)` and use its song ids, then `show_song` for details. (iii) For each playlist, call `show_playlist` and use `songs[*]`. Print the counts of each source and of the union. Deduplicate by (title, frozenset of artist names), and keep the artist order as given. Write plain rows `Title,Artist1|Artist2` with the header `Title,Artists`, and avoid quoting unless a field contains a comma. Re-read the file with `show_file` and check the row count equals the union count BEFORE calling `delete_account`. The deletion is irreversible, so if the count looks low (e.g. playlists contributed 0 songs), fix it first.

5. MESSAGE-DRIVEN TASKS ('X asked for ... via text'): FIRST read the conversation with that contact (`search_text_messages(phone_number=...)`, paginated, sorted by `sent_at`) and extract the exact criterion (e.g. 'movie from Quentin Tarantino', a genre, a director). Identify the contact by an exact first-name match in `search_contacts`. Then open the relevant note via `show_note`, and select ONLY entries that satisfy the criterion (e.g. entries whose ` - director:` line equals the requested director). Dedupe, print the selected titles, and send them comma-separated. Never send the full list when the request names a filter. If the note has per-item attributes, parse them per item block.

6. LOGIN: The phone app username is the phone number from `supervisor.show_profile()['phone_number']`, not the email. Use that first. All other apps use the email. Log in to each app before calling it, and re-login if you get a 401 (tokens may be lost between cells; keep the token in a variable, and do not paste tokens by hand).

7. Never use `.get(key, default)` or `if 'key' in resp` to hide missing data. Index directly, and assert that collections used for mutations or exports are non-empty or plausible. Do not call `complete_task()` while a printed count looks wrong or suspiciously zero.

8. Venmo request tasks (reject/approve/deny requests): use `show_received_payment_requests(status='pending')` with full pagination, and match `sender['email']` against the full paginated email set for each named relationship group. Print the group sizes, the pending total, the matched count, and the (id, sender) pairs before acting. Afterwards, re-fetch the pending list and confirm that none from the target senders remain.

REINFORCE (patterns that worked): the 'played so far' queue rule, the 'liked/downloaded' library cleanup, roommate bill splits, dinner payment requests, and Venmo totals all pass when you follow the playbook procedures exactly. Keep doing the discovery -> print -> mutate -> verify -> `complete_task()` sequence.
