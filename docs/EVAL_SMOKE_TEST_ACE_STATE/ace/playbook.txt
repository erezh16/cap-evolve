## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00042] When a task says 'reply/respond ... as per their request' (text message, email, etc.), FIRST read the incoming message from that contact to get the criteria (genre, director, count, etc.). Do this before building the reply. Never send an irreversible message (send_text_message, send_email, etc.) until you have seen both the request and the full source data. Sending an unfiltered 'everything' list is almost certainly wrong.
[shr-00054] For Venmo 'comment + like all payments I received from <friends/coworkers/...> in the last N days (including today)', follow misc-00053 exactly, whatever the relation or comment text. Use the comment string exactly as quoted in the task ('Thanks!' is not 'Thank you!'). Window start = today-(N-1), so N=7 gives today-6. Never go straight from collecting IDs to the comment/like writes. First run a READ-ONLY preview that prints (transaction_id, created_at, sender email, description, liked, comment_count) for every target. Read the like_transaction and show_transaction_comments docs before writing.
[shr-00058] PRE-WRITE GATE for Venmo (and any irreversible bulk write): do not call create_transaction_comment/like_transaction unless the immediately preceding step printed per-target rows (id, created_at, sender email, description, liked, comment_count) and the total count. A step that prints only a list of IDs does not count. For 'last N days including today', show_transactions must not use max_created_at. Printing the IDs and calling complete_task right after the writes is a failure pattern. After the writes, a read-back verify step is required before complete_task. Also use the comment text quoted in the current task, not the example text in misc-00053 ('Thank you!').
[shr-00062] PRE-SUBMIT GATE for 'most/least recommended/frequent <entity>' answers: the step that computes counts must NOT contain complete_task, and it must not contain a fallback such as `answer = names[0]` for ties (that is a silent tie-break). The sequence is three separate steps. (1) Paginate show_recommendations with `while True`, page_limit=20, and print len(recs) and recs[0]. (2) Dedupe by song_id and count artists keyed by a['id']. Print len(recs) vs len(uniq), the top 5 (name, count), and the number of artists tied at the top count. Check that sum(cnt.values()) == sum(len(r['artists']) for r in uniq). (3) Only after seeing that output and finding a unique top count, call complete_task(answer='<artist name only>') in its own step. If the top count is tied, re-inspect the data (duplicates, show_artist, show_following_artists) before choosing. Reference: the recommendations list for this account type returned 28 raw items on a past run (pages of 20), so the raw count alone is not proof of uniqueness.
[shr-00068] [Venmo 'already paid' = time-windowed evidence] For tasks like 'I paid the bill yesterday/on <date>; some people already sent their share; request money from the others', never build the paid set from all-time received transactions. Anyone who ever paid you (rent, old dinners, other splits) would be wrongly treated as paid. Compute the event date from phone.get_current_date_and_time() (yesterday = today-1) and USE it in the filter. Call show_transactions(direction='received', min_created_at=<event date>, page_limit=20, while True, no max_created_at) and keep a row only if created_at[:10] >= event date and the sender email is in the coworker email set. Print (transaction_id, created_at, sender email, amount, description) for each kept row, and compare each amount with that person's share in the note. Sanity check: if almost everyone (e.g. 6 of 7) appears 'already paid' when the task says 'some people', your filter is too loose, so recheck the dates. Print the final pending list before any create_payment_request call.

def paginate(api_func, **kw):
    pi = 0
    while True:
        page = api_func(page_index=pi, page_limit=20, **kw)
        if not isinstance(page, list) or not page:
            break
        for it in page:
            yield it
        pi += 1

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00015] Never silently `continue` when a per-item lookup fails or lacks the needed field; collect failures, print them, and confirm processed count == retrieved count before choosing a min/max. A strict '<' loop also hides ties by keeping the first item, so sort and print the bottom/top 3-5 values instead of tracking only a single best.
[cms-00016] Do not put apis.supervisor.complete_task(...) in the same code block as the computation of the answer. Compute and print evidence first; submit the title/number alone in a later step (complete_task is irreversible).
[cms-00018] Every Spotify list API needs pagination, not just show_playlist_library. This includes show_liked_songs, show_song_library, show_liked_albums, show_album_library and show_song_reviews. They require access_token and default to page_limit=5. Loop `while True` with page_index and page_limit=20 until an empty page, and check that the page is a list. A total of exactly 5 (or a multiple of the page size) means you probably fetched only one page, so re-fetch with pagination before using the set.
[cms-00023] Do not judge write-API success by the presence of a specific key such as 'song_review_id' unless the doc's response_schemas show it. Read the doc, or print one raw response, before writing the check. A dict like {'message': 'Updated ...'} is a success. Only treat the result as a failure if the message indicates an error (e.g. 'not found', 'invalid', 'unauthorized') or the later read-back shows the wrong value. Mislabelling successes as failures leads to confusing re-runs.
[cms-00026] [cms] Do not use a single 'skipped' counter for several reasons (not liked, already >= X, lookup failed). Keep separate counters and lists so the summary can be audited. Do not derive 'processed' by subtraction. For a 'liked' filter, derive the liked set from paginated show_liked_songs (or cross-check show_song_privates['liked'] against it) and print the target ids before any irreversible review_song/update_song_review call. Pass access_token to every Spotify list/read API, including show_song_reviews, after confirming in its doc.
[cms-00030] [cms] Do not wrap an irreversible write loop in `try/except` that appends to a `failed` list and then call complete_task() regardless. Treating 'no exception' as success without reading the write API's response_schemas hides errors such as already-liked or not-found. Print each response, stop and investigate if any failure occurs, and only complete after a read-back verification.
[cms-00031] Before logging in to any app, check show_api_doc(app, 'login') for what 'username' means (email vs phone number). Do not copy the Spotify/Venmo pattern (username=email) to the Phone app. A 401 'Invalid credentials' on login usually means the wrong username field, not a wrong password, so re-read the doc instead of retrying variants. Likewise, do not guess whether an API takes an access_token. Read its doc first (e.g. get_current_date_and_time takes none; search_contacts needs one).
[cms-00033] 'Terminate/delete my account' after a task about an app's data means THAT app's account (e.g. a Spotify backup -> apis.spotify.delete_account(access_token=spotify_token)). Never call delete_account on another app (e.g. file_system) just because its token is at hand. That deletes the wrong account and may wipe the file you just wrote. Run show_api_doc(<app>,'delete_account') first. Run the delete in its own step and print the response. Call complete_task() only in a later step.
[cms-00034] Never alter data to make a CSV 'well-formed' (e.g. replacing commas in titles or artists with spaces). Quote fields instead: use `import csv, io; buf=io.StringIO(); w=csv.writer(buf, lineterminator='\n'); w.writerow(['Title','Artists']); w.writerow([title,'|'.join(artist_names)]); content=buf.getvalue()` (csv and io are allowed; os is not). This keeps the exact titles and artist names. Use the separator the task specifies (e.g. '|') only between artist names.
[cms-00036] The `io` module is FORBIDDEN in this sandbox (error 'Usage of the following module is not allowed: io'), so cms-00034's io.StringIO recipe fails. Build CSV text without io. Option A: `import csv`, then use a tiny sink such as `class Sink:\n    def __init__(self): self.parts=[]\n    def write(self, s): self.parts.append(s)`, with `sink=Sink(); w=csv.writer(sink, lineterminator='\n'); w.writerow(['Title','Artists']); ...; content=''.join(sink.parts)`. Option B: write a manual escaper that quotes a field ONLY if it contains a comma, double quote or newline (doubling inner quotes). Keep the header exactly `Title,Artists` with NO quotes. Do not wrap every field in quotes, because a checker that compares raw text would see `"Title"` instead of `Title`. Join multiple artists with the requested separator (e.g. '|'). Sort rows (e.g. by song_id) so the output is deterministic rather than relying on set order.
[cms-00038] In this sandbox `os`, `io` AND `csv.writer` (and likely the other csv write helpers) are all blocked ('Usage of the following function is not allowed: csv.writer'). This makes cms-00034 and cms-00036 Option A unusable. Do not try the csv module for writing. Go straight to the manual escaper (cms-00036 Option B) and build the text with '\n'.join(lines)+'\n'. The header is the literal line `Title,Artists`. Join artist names with '|', and quote a field only if it contains a comma, double quote or newline (doubling inner quotes).
[cms-00044] phone.search_contacts(query='Christopher') returned ALL contacts (14), with the real match first only by luck. Never take contacts[0]. Filter explicitly, e.g. `[c for c in contacts if c['first_name']=='Christopher']`. Print the match and confirm that exactly one contact fits. If several fit, disambiguate using the request or relationship.
[cms-00045] Simple Note content with sub-lines (e.g. 'Interstellar\n - director: Christopher Nolan\n - genre: Sci-Fi, Drama') is structured data. Do not discard the '-' metadata lines to get titles. Print the FULL note content (not just [:200]), parse each entry into {title, director, genre}, and apply the filter from the request (match genre/director case-insensitively, and treat genre as a comma-separated list). Print the filtered titles and their count before sending. Do not put the parse and the send in the same block.
[cms-00047] Never filter Simple Note data with a hardcoded list from your own memory (e.g. a list of a director's films) plus substring search over all notes. It misses titles that are not on your list and it matches titles in unrelated notes. Instead, find the movie-recommendation note (search_notes(query='movie'), or print every note title), then show_note and print its FULL content. Parse entries with their '- director:' and '- genre:' lines, and keep only entries whose metadata matches the request (e.g. director == 'Quentin Tarantino', case-insensitive). The reply must come from the note's own metadata, so print the parsed entries and the filtered titles with their count before sending.
[cms-00051] Pagination applies to EVERY app, not just Spotify/Venmo. Phone search_contacts(query, access_token, page_index, page_limit<=20) defaults to page_limit=5 and returns the first 5 contacts alphabetically. Getting exactly 5 contacts (e.g. Alexander, Anita, Brenda, Cheryl, Connor) means only page one was fetched, and the account has more (~14). 'Small list, no pagination needed' is never a valid assumption. Read show_api_doc('phone','search_contacts'), loop `while True` with page_limit=20 until an empty or non-list page, and print the total before filtering by relationship. Building a relationship email set (coworker, roommate, sibling) from page one alone silently drops people. Any irreversible comment/like/send done on that partial set cannot be undone.
[cms-00055] Never use `resp.get('message')` or `isinstance(resp, dict) and 'message' in resp` as a success test for Venmo write APIs.
